01 What is Cloud Computing?

Before understanding AWS, you must understand what "the cloud" actually means — because it's not magical.

Cloud computing simply means: renting someone else's computer over the internet.

That's it. Amazon, Google, and Microsoft own massive data centers with hundreds of thousands of physical computers. They rent out pieces of those computers to people like you and me. You pay by the hour, like renting a car instead of buying one.

Imagine you need a shop to sell something. You have two choices:

Option A (Traditional): Buy land, build a shop, buy electricity, hire security, maintain the building forever. Very expensive upfront. Takes months.

Option B (Cloud): Rent a space in a mall. Pay monthly. Mall handles electricity, security, cleaning. You can get a bigger/smaller shop in 5 minutes. Start in a day.

The mall = AWS. Your shop = your EC2 server. You just rent the space.

Why is this better than running your own server at home?

  • Your home internet goes down → your app dies. AWS has 99.99% uptime.
  • Your home computer crashes → you lose data. AWS has automatic backups.
  • 1000 users hit your app → your home PC can't handle it. AWS can scale in seconds.
  • Your home IP changes every day. AWS gives you a fixed public IP.

02 What is AWS?

AWS = Amazon Web Services. It is Amazon's cloud platform. Launched in 2006, it is the largest cloud provider in the world. More than 33% of the internet runs on AWS — Netflix, Airbnb, NASA, NASA, even the CIA use AWS.

AWS has over 200 services. You don't need to know all of them. For a beginner deploying a FastAPI app, you only need these 5:

AWS ServiceWhat It DoesAnalogy
EC2Virtual computer/serverThe actual shop space you rent
S3File storage (like Google Drive)A warehouse to store files
RDSManaged database (PostgreSQL/MySQL)A managed filing cabinet
Route53Domain name management (DNS)The address/signboard of your shop
Elastic IPPermanent public IP addressA permanent phone number

For now, you only need EC2 and Elastic IP. That's it.

03 What is EC2?

EC2 = Elastic Compute Cloud. It is a virtual machine (VM) that runs in Amazon's data center. When you "launch an EC2 instance," Amazon creates a virtual computer for you. This computer has:

  • A CPU (how fast it can compute)
  • RAM (how much it can hold in memory)
  • Storage/Disk (how much data it can store permanently)
  • A public IP address (so the internet can reach it)
  • An operating system (Ubuntu Linux, in our case)
Your laptop is a computer. EC2 is also a computer — it just lives in Amazon's building in Mumbai instead of on your table. The only difference: you can't physically touch it. You control it entirely through your terminal by typing commands over SSH (Secure Shell). SSH is like a remote control for a computer.

What does "Elastic" mean?

It means you can resize it. If you start with a small server (1 CPU, 1GB RAM) and your app gets popular, you click a button and upgrade to 8 CPUs and 32GB RAM — in 2 minutes. You can also shrink it back. That flexibility is "elastic." No physical hardware to buy.

What is an Instance?

Each running EC2 virtual machine is called an instance. You can run 1 instance or 100 instances. Each instance is completely separate — its own OS, its own IP, its own data. Think of each instance as a separate computer.

Instance Types — t2.micro, t3.medium, etc.

EC2 has hundreds of instance types. The name tells you its power. For beginners, use t2.micro:

Instance TypevCPURAMUse CaseCost/month
t2.micro11 GBLearning, small appsFree (first year)
t3.small22 GBSmall production apps~$15
t3.medium24 GBMedium apps, teams~$30
t3.large28 GBMultiple services~$60
✓ Free Tier
New AWS accounts get 750 hours/month free of t2.micro for 12 months. That's enough to run 1 server 24/7 for free for an entire year. Always pick t2.micro when learning.

04 6 Core Concepts — Explained Deeply

Concept 1 — AMI (Amazon Machine Image)

When you launch an EC2 instance, the first question is: what operating system should it have? You pick this using an AMI.

An AMI is a frozen snapshot of a fully-configured operating system. AWS has thousands of public AMIs. When you select one, your EC2 instance boots with that OS already installed and ready — just like buying a laptop that already has Windows installed.

Imagine buying a brand new hard drive. You can install an OS from scratch (takes 2 hours), OR you can clone it from a pre-configured template that already has everything set up (takes 30 seconds). An AMI is that template.

For your FastAPI app, choose: Ubuntu Server 22.04 LTS (HVM), SSD Volume Type — it's free tier eligible and widely used.

LTS = Long Term Support. Ubuntu promises security updates for 5 years. Never use non-LTS versions on a server.

Concept 2 — Security Group (The Firewall)

This is the most important concept for beginners because most people's deployments fail because of Security Groups.

A Security Group is a virtual firewall. By default, ALL incoming traffic to your EC2 is BLOCKED. Nobody can reach your server — not even you. You must manually add rules to open specific ports.

What is a Port?

Ports are like different doors of a building. Your server is the building. Each service inside the server listens on a specific door (port number). When someone wants to talk to that service, they knock on that door.

PortServiceWho knocks on this door?
22SSHYou, from your terminal, to control the server
80HTTPBrowsers, when visiting http://yoursite.com
443HTTPSBrowsers, when visiting https://yoursite.com
8000FastAPI (uvicorn)Anyone testing your API directly
5432PostgreSQLYour app, connecting to the database

When you create a Security Group, you add Inbound Rules:

# Example Security Group Inbound Rules for your FastAPI server:

Type         Protocol  Port   Source
------       --------  -----  ------------------
SSH          TCP       22     My IP (only your computer)
HTTP         TCP       80     Anywhere (0.0.0.0/0)
HTTPS        TCP       443    Anywhere (0.0.0.0/0)
Custom TCP   TCP       8000   Anywhere (0.0.0.0/0)

# "Anywhere" means anyone on the internet can reach that port.
# "My IP" means ONLY your specific home/office IP can reach that port.
# Always restrict SSH to "My IP" — never open port 22 to everyone.
⚠ Critical Security Warning
Never set SSH (port 22) source to "Anywhere (0.0.0.0/0)". Hackers constantly scan the internet for open port 22 and try to brute-force access. Always set SSH to "My IP" only.

Concept 3 — Key Pair (How You Log In)

Your EC2 server has no screen, no keyboard, no monitor. You can't physically touch it. The only way to access it is through your terminal using a protocol called SSH (Secure Shell).

But you need to prove you're the owner before the server lets you in. AWS doesn't use passwords for this (passwords can be guessed). Instead it uses cryptographic key pairs.

AWS generates two mathematically-linked keys:

  • Public Key — AWS keeps this on your server. It's like a padlock.
  • Private Key — You download this as a .pem file. It's the key that opens the padlock. Only someone with this file can log in.
Imagine a diary with a padlock (public key). Only the matching key (private key = your .pem file) can open that padlock. Amazon puts the padlock on your server. You keep the key. When you SSH in, your computer shows the server the key, the server checks it matches the padlock, and lets you in.
⚠ You can NEVER download the .pem file again after the first time
Once you close the download dialog, the private key is gone from AWS forever. If you lose your .pem file, you cannot SSH into your server ever again. You'd have to create a new server. Save it in 2 places (your laptop + Google Drive).

Why does the .pem file need chmod 400?

When you run chmod 400 yourkey.pem, you're setting the file permission so only you can read it. SSH refuses to work if your key file is readable by other users on your computer — it's a security protection. chmod 400 = Owner can read, nobody else can do anything.

chmod 400 ~/Downloads/fastapi-key.pem

# chmod = change mode (change file permissions)
# 4 = read permission
# 00 = no permission for group, no permission for others
# So: only you can read this file. Nobody else.

Concept 4 — Elastic IP (Permanent Public IP)

Every EC2 instance gets a public IP address when it starts. But by default, this IP changes every time you stop and start the server.

This is a huge problem:

  • You tell someone your API is at http://65.0.12.34:8000
  • You stop the server at night (to save money)
  • Next morning you start it again → it gets a new IP: http://65.0.78.99:8000
  • The old URL is now broken. Everyone loses access.

An Elastic IP is a static (fixed) public IP address that you own. You associate it with your EC2 instance. Now no matter how many times you stop/start the server, the IP never changes.

Think of a regular IP like a temporary phone number that changes every month. An Elastic IP is like a permanent number you own forever. You can even detach it from one phone and attach it to another.
💡 Elastic IP Cost Warning
Elastic IPs are FREE as long as they are attached to a running EC2 instance. But if your server is STOPPED and the Elastic IP is idle (not used), AWS charges you ~$0.005/hour (~$3.60/month). To avoid charges: either keep your instance running, or release the Elastic IP when not in use.

Concept 5 — VPC and Subnets

VPC = Virtual Private Cloud. It is a private, isolated section of the AWS network that belongs to you.

Think of AWS as a giant apartment building. A VPC is your private apartment — nobody else can enter unless you invite them. All your EC2 instances, databases, and other services live inside your VPC.

A Subnet is a smaller section inside the VPC — like rooms inside your apartment.

  • Public Subnet — has a route to the internet. EC2 instances here can be accessed from outside.
  • Private Subnet — NO route to the internet. Used for databases — you never want your database directly accessible from the internet.
ℹ Good news for beginners
AWS automatically creates a default VPC with public subnets in every region for new accounts. You don't need to configure anything. Just use the default VPC when launching EC2. You'll learn custom VPCs when building more complex, production systems.

Concept 6 — Regions and Availability Zones

AWS has physical data centers around the world. These are grouped into:

Regions — A geographic location (e.g., Mumbai, Virginia, Frankfurt). Each region is completely independent. If one entire region goes down (rare), others are unaffected. Pick the region closest to your users for lowest latency.

Availability Zones (AZs) — Multiple isolated data centers within one region (e.g., Mumbai has 3 AZs: ap-south-1a, ap-south-1b, ap-south-1c). If one building catches fire, the others keep running.

For a beginner from India: use ap-south-1 (Mumbai). It's the closest and cheapest for Indian users.

05 How Docker Fits In

You already have a Dockerfile in your project. Let's understand what it does and why it matters on EC2.

Why Docker?

The classic developer problem: "It works on my machine!"

Your laptop has Python 3.10, specific library versions, and specific settings. Your EC2 server is a fresh Ubuntu with nothing installed. If you just copy your code and run it, it will fail because of missing dependencies.

Imagine packing for a trip. Instead of writing "bring these 47 specific items," you just bring your entire room — the exact environment you need. Docker containers are that "packed room." The container includes your app, Python, all libraries, config — everything. It runs identically everywhere.

Your Dockerfile — Line by Line Explained

Here is your Dockerfile with every line explained:

FROM python:3.10-slim
# This is the base image. Think of it as a pre-built foundation.
# python:3.10-slim = a minimal Linux OS with Python 3.10 already installed.
# "slim" means it stripped out unnecessary packages → smaller image = faster deployment.
# Without this, you'd need to install Python yourself.

WORKDIR /app
# Sets the working directory INSIDE the container.
# All subsequent commands run from this folder.
# Like typing "cd /app" — creates the folder if it doesn't exist.
# Your project files will live at /app/ inside the container.

COPY requirements.txt .
# Copies requirements.txt from your local machine INTO the container's /app/ folder.
# The "." at the end means "current directory" (which is /app because of WORKDIR).
# We copy ONLY requirements.txt first (not all code) for Docker caching optimization:
# If you change your code but not your requirements, Docker reuses the pip install layer.
# This saves minutes during repeated builds.

RUN pip install --no-cache-dir -r requirements.txt
# RUN executes a command during the build process (not at runtime).
# pip install = installs all Python packages listed in requirements.txt
# --no-cache-dir = don't save pip's download cache inside the image.
#                  Keeps the image smaller. Cache in a container is useless anyway.
# -r requirements.txt = read the list of packages from this file.

COPY . .
# Copies EVERYTHING from your local project folder into the container's /app/ folder.
# First "." = source (your local project)
# Second "." = destination (container's current directory = /app)
# This copies main.py/app.py, the SQLite db config, and all other files.

CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
# CMD is the command that runs when the container STARTS (not during build).
# uvicorn = the ASGI web server that runs your FastAPI app.
# "app:app" = filename:variable — your file is app.py and FastAPI instance is named app.
# --host 0.0.0.0 = CRITICAL! Means "listen on ALL network interfaces."
#   Without this, FastAPI listens only on 127.0.0.1 (localhost inside container).
#   Docker port mapping can't reach it. Your app would be invisible even on the same machine!
# --port 8000 = listen on port 8000 inside the container.
⚠ Bug in Your Original Dockerfile
Your original Dockerfile had two bugs:

1. requiremnts.txt → missing letter 'e' → should be requirements.txt
2. main:app → your file is named app.py, not main.py → should be app:app

Docker Run Command — Explained

docker run -d --name fastapi-container -p 8000:8000 --restart always fastapi-app

# docker run = create and start a new container from an image
# -d = detached mode. Runs in the background. Without this, the container runs in
#      your terminal and stops when you close the terminal.
# --name fastapi-container = give the container a human-readable name.
#   Without this, Docker assigns a random name like "happy_curie". Naming makes management easier.
# -p 8000:8000 = port mapping. Format is HOST_PORT:CONTAINER_PORT.
#   Left 8000 = port on the EC2 server (the outside world).
#   Right 8000 = port inside the container.
#   This says: "Forward all traffic coming to EC2's port 8000 into the container's port 8000."
#   You could do -p 80:8000 — then http://yourip (no port needed) would reach FastAPI!
# --restart always = if the container crashes or the server reboots, restart automatically.
#   This keeps your app alive 24/7 without manual intervention.
# fastapi-app = the name of the image to run (what you named it in docker build -t fastapi-app .)

06 The Full Picture — How Everything Connects

Here is the complete journey of a request from a user to your FastAPI app:

User's browser
    │
    │  types: http://65.0.12.34:8000/api/v1/login
    │
    ▼
Internet
    │
    │  traffic reaches AWS network
    │
    ▼
Elastic IP  (65.0.12.34 — your permanent IP)
    │
    │  resolves to your EC2 instance
    │
    ▼
Security Group  (firewall check)
    │  ✓  Port 8000 is in the allowed inbound rules
    │  ✗  Port 3000 would be BLOCKED here (no rule for it)
    │
    ▼
EC2 Instance  (Ubuntu Linux server)
    │
    │  Docker receives the request on port 8000
    │  Port mapping -p 8000:8000 forwards it inside the container
    │
    ▼
Docker Container
    │
    │  Uvicorn (web server) receives the request
    │  Routes it to FastAPI
    │
    ▼
FastAPI app  (your app.py)
    │
    │  /api/v1/login endpoint runs
    │  Queries SQLite database (app.db)
    │  Returns JWT token
    │
    ▼
Response travels back → Container → EC2 → Internet → User's browser

07 Step-by-Step Deployment Guide

Step 1 — Launch EC2 Instance (AWS Console)

Go to: AWS Console → EC2 → Launch Instance

Name:           my-fastapi-server
AMI:            Ubuntu Server 22.04 LTS  ← search and select this
Instance type:  t2.micro  ← Free tier eligible
Key pair:       → Click "Create new key pair"
                → Name: fastapi-key
                → Type: RSA
                → Format: .pem
                → Click Create  ← FILE DOWNLOADS AUTOMATICALLY. SAVE IT!
Security Group: → Create new
                → Add rule: SSH, Port 22, My IP
                → Add rule: HTTP, Port 80, Anywhere
                → Add rule: Custom TCP, Port 8000, Anywhere
Storage:        20 GB  ← change from default 8 GB

→ Click "Launch Instance"
→ Wait 1-2 minutes for it to start
→ Go to EC2 → Instances → you'll see your server with "Running" status

Step 2 — Get an Elastic IP

# In AWS Console:
# 1. Left sidebar → Network & Security → Elastic IPs
# 2. Click "Allocate Elastic IP address"
# 3. Leave all defaults → Click "Allocate"
# 4. Select the new IP → Actions → "Associate Elastic IP address"
# 5. Instance: select your EC2 → Click "Associate"
# Now copy this IP address — you'll use it in every command below.

Step 3 — SSH Into Your Server

Open your terminal. Do this from your local computer, not inside AWS console.

# For Mac / Linux:
chmod 400 ~/Downloads/fastapi-key.pem

ssh -i ~/Downloads/fastapi-key.pem ubuntu@YOUR_ELASTIC_IP

# For Windows (Git Bash or WSL):
# Move fastapi-key.pem to C:\Users\YourName\
# Then run:
ssh -i /c/Users/YourName/fastapi-key.pem ubuntu@YOUR_ELASTIC_IP

# First time: it asks "Are you sure you want to continue connecting? (yes/no)"
# Type: yes  → press Enter
# You're in! You'll see the Ubuntu prompt:
# ubuntu@ip-172-xx-xx-xx:~$
ℹ Why "ubuntu"?
The default username for Ubuntu AMI is ubuntu. For Amazon Linux AMI it would be ec2-user. Always use ubuntu for Ubuntu servers.

Step 4 — Install Docker on EC2

You are now inside your EC2. Run these commands:

# Update package lists (always do this first on a fresh server)
sudo apt-get update -y

# Install prerequisites
sudo apt-get install -y ca-certificates curl

# Add Docker's signing key (security verification)
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Add Docker's official repository to apt sources
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
  https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker
sudo apt-get update -y
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

# Add yourself to docker group (avoid typing "sudo" before every docker command)
sudo usermod -aG docker ubuntu

# Apply group change immediately (or log out and log back in)
newgrp docker

# Verify Docker works
docker --version
# Expected output: Docker version 24.x.x

Step 5 — Upload Your Project to EC2

Open a new terminal tab on your local machine (don't close the SSH one). We use scp (Secure Copy) to transfer files over SSH.

# scp = secure copy. Works exactly like cp but over SSH.
# Format: scp -i keyfile source destination
# For a folder, add -r (recursive)

scp -i ~/Downloads/fastapi-key.pem -r ./employee-api ubuntu@YOUR_ELASTIC_IP:/home/ubuntu/app

# ./employee-api = your local project folder path
# ubuntu@YOUR_IP:/home/ubuntu/app = destination on the server
# This creates /home/ubuntu/app/ on your EC2 with all your files inside

# Or using git (easier for future updates):
# First, push your code to GitHub. Then on the EC2:
sudo apt install -y git
git clone https://github.com/yourusername/your-repo.git /home/ubuntu/app

Step 6 — Fix Your Dockerfile and Build

Go back to your SSH terminal (inside EC2):

# Navigate to the uploaded folder
cd /home/ubuntu/app

# List files to confirm everything is there
ls -la
# Should show: app.py  Dockerfile  requirements.txt

# Edit the Dockerfile to fix the two bugs
nano Dockerfile
# Change "requiremnts.txt" → "requirements.txt"
# Change "main:app" → "app:app"
# To save: Ctrl+X → press Y → press Enter

# Build the Docker image
# -t fastapi-app = tag (name) the image "fastapi-app"
# . = build context is current directory (looks for Dockerfile here)
docker build -t fastapi-app .
# You'll see output like:
# Step 1/5 : FROM python:3.10-slim
# Step 2/5 : WORKDIR /app
# ...
# Successfully built abc123def456
# Successfully tagged fastapi-app:latest

# Run the container
docker run -d --name fastapi-container -p 8000:8000 --restart always fastapi-app

# Verify it's running
docker ps
# Should show:
# CONTAINER ID  IMAGE        COMMAND         STATUS         PORTS
# a3f2b1c4d5e6  fastapi-app  "uvicorn..."    Up 30 seconds  0.0.0.0:8000->8000/tcp

Step 7 — Test Your Live API

# Option 1: Test from inside EC2 (curl)
curl http://localhost:8000/docs
# Should return HTML of FastAPI docs page

# Option 2: Open in your browser
# Type this in Chrome/Firefox/Edge:
http://YOUR_ELASTIC_IP:8000/docs

# You should see the FastAPI Swagger UI — interactive documentation.
# Try the /api/v1/register endpoint right there in the browser!

08 Bugs in Your Code — Fixed

Bug 1 — Dockerfile Filename Typo

# ORIGINAL (broken):
COPY requiremnts.txt .

# FIXED:
COPY requirements.txt .

When Docker runs COPY requiremnts.txt ., it looks for a file literally named requiremnts.txt in your project. It doesn't exist. Build fails with "COPY failed: file not found".

Bug 2 — Wrong Module Name in CMD

# ORIGINAL (broken):
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

# FIXED:
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

Uvicorn's format is "filename:variable". Your Python file is named app.py and your FastAPI instance is created as app = FastAPI(). So it must be "app:app". If you name it "main:app", uvicorn looks for a file called main.py, can't find it, and crashes immediately.

Two solutions:

  • Change CMD to "app:app" (recommended — no file rename needed)
  • Rename your file from app.py to main.py and keep CMD as "main:app"

09 Command Cheat Sheet

SSH Commands

# Connect to server
ssh -i fastapi-key.pem ubuntu@YOUR_IP

# Disconnect from server
exit

# Copy files TO server
scp -i fastapi-key.pem -r ./my-folder ubuntu@YOUR_IP:/home/ubuntu/

# Copy files FROM server to local
scp -i fastapi-key.pem ubuntu@YOUR_IP:/home/ubuntu/app/app.db ./local-backup/

Docker Commands

# Build image from Dockerfile in current folder
docker build -t fastapi-app .

# Run container (detached, named, port-mapped, auto-restart)
docker run -d --name fastapi-container -p 8000:8000 --restart always fastapi-app

# See running containers
docker ps

# See ALL containers (including stopped)
docker ps -a

# View live logs
docker logs -f fastapi-container

# Stop container
docker stop fastapi-container

# Start stopped container
docker start fastapi-container

# Restart container
docker restart fastapi-container

# Delete container (must stop first)
docker stop fastapi-container && docker rm fastapi-container

# Redeploy after code changes:
docker stop fastapi-container
docker rm fastapi-container
docker build -t fastapi-app .
docker run -d --name fastapi-container -p 8000:8000 --restart always fastapi-app

# Get a bash shell INSIDE a running container (for debugging)
docker exec -it fastapi-container bash

Linux Commands You'll Use Often

# Check disk space
df -h

# Check RAM usage
free -h

# Check what's running on a port (e.g. port 8000)
sudo lsof -i :8000

# See all running processes
ps aux

# See real-time CPU/RAM usage
htop   (install with: sudo apt install htop)

# Edit a file
nano filename.txt   # Ctrl+X to exit, Y to save

# See file contents
cat filename.txt

# List files in current folder (with details)
ls -la
